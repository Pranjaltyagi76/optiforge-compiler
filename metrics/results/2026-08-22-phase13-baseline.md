## 8. Analysis (written by hand)

The corpus is ten programs now: the eight Phase 12 measured, plus `matmul.of`
and `sieve.of`, which arrays made writable. This is the first run of the full
set.

**Two independent sessions, both committed.** `methodology.md` §4 calls a
difference real only if it exceeds the noise floor, the spreads do not overlap,
**and it reproduces in a second session**. The third condition was never
actually exercised before; it is here, because the machine was noisy enough
that it had to be. Session A is the table above; session B is a second
`-O2`-versus-PGO run taken later
([raw](../raw/2026-08-22-fa3e1f7/published/phase13-baseline-b.json)).

| Program | Session A | Session B | Verdict |
|---|---:|---:|---|
| `branch_machine.of` | +16.2% | +16.0% | **win, reproduced** |
| `matmul.of` | +9.3% | +13.3% | **win, reproduced** |
| `sieve.of` | +8.2% | +7.6% | **win, reproduced** |
| `nested_math.of` | +4.4% | +7.1% | **win, reproduced** |
| `loop_sum.of` | +4.1% | +2.9% | **win, reproduced** |
| `biased_branch.of` | +0.6% | +0.7% | inside the floor |
| `branchy.of` | +0.6% | −0.4% | inside the floor |
| `nbody.of` | −0.6% | −0.5% | inside the floor |
| `recursive_fib.of` | −1.5% | +0.1% | inside the floor |
| `loop_kernel.of` | −5.6% | −5.9% | **loss, reproduced** |

**Five benchmarks beat `-O2` above the noise floor in both sessions**, against
three in Phase 12. Both of the new ones are among them.

### The two benchmarks arrays unblocked

**`matmul.of`, +9.3% and +13.3%.** The strongest new result, and the mechanism
is the one this benchmark was written to force. `multiply`'s innermost loop runs
`size` times per entry, and `size` is a **runtime parameter** — nothing static
can know it. The profile measures it at exactly 64 and the unroller takes factor
8. The emitted function goes from 173 instructions to 365, and the loop is the
shape that pays for it: one accumulator, two loads, a multiply-add, no calls,
and — the part that matters — **peak live values stay at 10 and spills stay at
3**, unchanged from `-O2`. Replicating this body costs nothing in register
pressure, so the removed back-edge jumps are pure gain.

The 4-point gap between sessions is worth naming rather than averaging away. Its
spread is 3.9% and 3.6%, both over the 3% gate, so the honest statement is
"between 9 and 13 percent" and not a single figure.

**`sieve.of`, +8.2% and +7.6%.** Two loops get unrolled: the 50,000-iteration
clear loop, and the strided marking loop at a measured average trip count of
1,943. The second is the interesting one — its *actual* trip count varies from
thousands (for p=2) to zero (for most primes), and 1,943 is an average no static
heuristic could produce or defend. Unrolling on an average is safe here only
because every copy re-tests the exit condition, which is the design decision
Phase 11 made for exactly this case.

Spills stay at 0 and peak pressure at 5, again unchanged by unrolling.

### What the wins have in common, and what the loss does not

Compare the three programs the unroller helps with the one it hurts:

| Program | peak live, `-O2` → PGO | spills, `-O2` → PGO | result |
|---|---|---|---|
| `matmul.of` | 10 → 10 | 3 → 3 | **+9 to +13%** |
| `sieve.of` | 5 → 5 | 0 → 0 | **+8%** |
| `nested_math.of` | 5 → 5 | 0 → 0 | **+4 to +7%** |
| `loop_kernel.of` | 12 → 12 | 7 → 8 | **−6%** |

`loop_kernel.of` is the only one already **over the eight allocatable integer
registers** before unrolling, and the only one that loses. That is a strong
hint, and §10 records it as the hypothesis the unroller cost model should be
built on — but it is a hint from four data points and it is not yet a
demonstrated cause. The spill count barely moves (7 → 8), so if pressure is the
mechanism it is acting through something other than the number of spilled
values, and the next step is to count instructions in the emitted inner loop
rather than to guess again.

### Everything else

Unchanged in substance from Phase 12, and the two sessions agree on all of it:
`biased_branch` is dominated by an `idiv`, `branchy`'s loop is a call the
unroller refuses, `recursive_fib` has no loops, and `nbody` is where
profile-weighted spill costs do slight harm.

`branch_machine.of` reproduces at +16.2% and +16.0% — the most stable number in
the project.

## 9. Anomalies and threats to validity (written by hand)

**Four of ten programs breach the Q-02 spread gate**, and this is the run's
main weakness. The samples are bimodal — a program that normally takes 200 ms
occasionally takes 450 ms, in every configuration alike. The pattern is
consistent with the machine periodically doing something else (the harness
writes fresh executables on every run, which on Windows invites a scan of each
one), and it is not something the compiler or the benchmark controls.

What was done about it, in order:

1. A first session was taken and **discarded**: `sieve.of` showed a 97.6%
   IQR/median, which is not a measurement. It is mentioned because deleting it
   silently would be the dishonest version of this paragraph. Its medians
   agreed with what was kept, which is the only reason the discard is not itself
   a selection effect — but a discarded session is a discarded session.
2. Repetitions were raised from 15 to 21.
3. **A second session was taken and committed**, so the reproduction condition
   in `methodology.md` §4 is satisfied by evidence rather than by assertion.

The medians are robust to this kind of interference — an occasional long run
moves a median very little — and the two sessions agree on the sign of all ten
programs and on the magnitude of eight of them. The four wide rows should be
quoted as ranges, not as single figures, and the table above does that.

**The wins were designed for.** `matmul.of` was written to have an inner loop
whose trip count only a profile can know, and it does. That demonstrates the
mechanism works; it is not evidence about how often the mechanism meets code
nobody wrote for it.

**`sieve.of` is not memory-bound.** Its 400 KB working set is L2-resident on
this machine. It brings a strided access pattern the corpus did not have, which
is worth something, but the "no memory-bound benchmark" gap Phase 12 recorded is
**narrowed, not closed**, and closing it needs heap allocation.

**The startup offset applies to every figure here.** 61 ms of each measurement
is process spawn (`methodology.md` §4), so every percentage above understates
the speedup on the generated code. `matmul.of`'s +9.3% is +11.5% on the work.
The whole-process figures are what is reported, deliberately.

**Compile time moved the wrong way once.** `sieve.of` compiles in 0.59 s at
`-O2` and 0.48 s with a profile — a P-05 ratio below 1, which is not physically
meaningful and is a single unrepeated sample. The compile-time column remains
one measurement per cell and should not be read finely.
