## 8. Analysis (written by hand)

The noise floor on this machine is **1.0%**
([machine spec](../machines/windows-mingw.md)). Three programs clear it, one
loses by more than it, four sit inside it. Each is named below; nothing is
dropped for being inconvenient.

Every attribution figure quoted here comes from the separate sweep in
[`2026-08-20-pgo-attribution.md`](2026-08-20-pgo-attribution.md), which disables
one profile-guided decision at a time. No claim below rests on inspection alone.

**What moved, and why.**

**`branch_machine.of`, +15.8% — and 16.0 of those points are block layout.**
This is the largest result the project has produced, and it is the cleanest.
`step` is a four-state dispatch chain in which the workload leaves the machine
in one state about 98% of the time, so there is a single path through the
function that almost every call takes. Nothing static can see that: to the
compiler `input % 97 == 0` is a comparison like any other. With the profile,
layout puts that path on the fall-through, inverts the conditions so the common
arm is not the branch taken, and sinks the three rare transition arms and the
cold `report` call past the return. The emitted function shrinks from 154
instructions to 149, which is not the point — the point is that the 149 are in
the order the processor walks them. Disabling layout alone returns the whole
gain to −0.1%.

**`nested_math.of`, +5.2%, from unrolling.** Phase 11 measured 5.5% for this
program and predicted 5.8% from the instruction arithmetic; this run says 5.2%
and the attribution sweep credits +5.0 of it to `unroll`. Three independent
measurements of the same mechanism agreeing to within 0.6 points is the reason
to believe any of them.

**`loop_sum.of`, +2.1%, also unrolling** (+2.6 attributed). Same mechanism as
`nested_math` with a longer loop body, so the back-edge jump that unrolling
removes is a smaller share of each iteration. Two points against a 1.0% floor is
a real but small result and is reported as one.

**What did not move, and why not.**

| Program | PGO | Why nothing happened |
|---|---:|---|
| `biased_branch.of` | +0.4% | Layout does the right thing and it does not matter: the loop contains an `idiv`, which costs more than every branch around it put together. Predicted in `System_design.md` §16.5, measured in Phase 11, unchanged here. |
| `branchy.of` | −0.0% | The unroller refuses its loop, deliberately — the body is a call, and Phase 11 added that guard after unrolling made this program *slower*. The guard is still doing its job. |
| `recursive_fib.of` | −0.7% | No loops at all, and a two-block hot function. There is nothing for layout to reorder and nothing for the unroller to copy. |
| `nbody.of` | −0.4% | The only program where profile-weighted spill costs measurably *hurt* (−1.5 attributed to `regalloc`). See below. |

**Where PGO lost.**

**`loop_kernel.of`, −7.1%, and −6.8 of that is the unroller.** This is the
showcase benchmark, built so that loop depth — the only static heat signal this
compiler has — ranks its two loops backwards. The profile does correct the
ranking: the remarks show it unrolling the depth-1 loop that runs 350,000,000
times and leaving the depth-2 nest that runs 400 times alone, which is exactly
the decision the benchmark was written to force. **Getting the decision right
and still losing 7% is the finding.**

The mechanism is visible in §5. Unrolling by 8 takes the function from 129
emitted instructions to 282 and the allocator from 40 coloured units to 123.
What unrolling buys is seven back-edge jumps per eight iterations; what it costs
here is a loop body that no longer fits the machine's front end, over a
dependency chain (`a6` needs `a5`, `a8` needs `a7` and `a6`, `a9` needs `a8` and
`a5`) that already limits the loop to roughly 2.5 cycles per iteration. There
were never any stalled cycles for the removed jumps to fill.

Two things follow, and only the first is about this benchmark:

1. The unroller has no cost model. It has a trip-count threshold and a
   body-shape guard, and neither of them can express "this body is already
   issue-limited". Phase 11's open action *"true unrolling with a remainder
   loop"* would remove the per-copy exit test but would not fix this; what is
   missing is a reason not to unroll.
2. **This was not fixed before reporting it.** Phase 11 fixed `branchy.of`'s
   regression the same day it found it, and that was right, because the fix
   there was a categorical guard — never unroll a loop containing a call —
   derivable without reference to the benchmark that exposed it. There is no
   equivalent here: any threshold that rescues `loop_kernel.of` would be a
   number tuned against `loop_kernel.of`, which is the failure `methodology.md`
   §2 warns about in the other direction. It is recorded as an action instead.

**`nbody.of`, −0.4%, of which regalloc is −1.5%.** The one place profile-weighted
spill costs did harm. Its `simulate` holds 35 values live against the 10
allocatable XMM registers (xmm6–xmm15; the rest carry arguments or are scratch),
so the allocator is spilling either way; the profile tells it that
every block in the function is equally hot, because the function *is* one loop,
which is true and useless. It replaces a loop-depth ranking that at least
distinguished the entry block from the body with a flat one that does not. Under
PGO the spill count goes from 38 to 64 — though most of that is unrolling
enlarging the live set, not the weighting itself.

## 9. Anomalies and threats to validity (written by hand)

**The two missed targets.**

*P-05 = 1.73x on `nbody.of`.* Compiling with a profile takes 0.88 s against
0.51 s without. The cause is the same unrolling that costs it runtime: eight
copies of a 128-unit block make the allocator's interference graph far more
expensive to build. The target is breached on one program of eight and the
absolute figure is under a second, so this is recorded rather than treated as a
blocker — but it is a real breach, and the ratio will get worse on larger inputs
rather than better. Note also that every compile-time figure in §7 is a **single
measurement**, not a median: `loop_kernel.of`'s 0.81x is below 1.0, which is not
physically meaningful and is simply that sample's noise.

*G-01 = 1 benchmark over 10%, not 3.* This is the project's headline target and
it is missed. Section 8 says where each of the other seven went. The honest
summary is that this compiler's profile-guided decisions are worth a great deal
on one program shape — a branchy dispatch with a dominant path — and worth
roughly nothing to slightly negative on the rest, because the two decisions with
real leverage (layout and unrolling) each apply to a narrow shape, and the
unroller currently has no cost model. The Phase 12 exit criterion — three
benchmarks beating `-O2`, with the wins explained mechanistically — is met.
NFR-10's ≥10% on three benchmarks is not.

**Threats.**

- **Eight programs, all synthetic, all written by the person measuring them.**
  The language has no arrays, so `matmul`, `sieve` and a physically real `nbody`
  — three of the six shapes `methodology.md` §2 asks for — cannot be written.
  What stands in for them is documented in the Phase 12 evaluation. The corpus
  is compute-bound throughout, with no memory-bound member at all, and a
  memory-bound benchmark is where block layout and cold-code placement would be
  expected to pay most.
- **`branch_machine.of` was the showcase for layout and it is also the program
  with the worst measured spread** (5.2% IQR/median in the noise-floor session,
  though 0.5–1.3% in this one). Its +15.8% is far above either figure, so the
  conclusion is safe, but the number itself should be quoted as "about 16%".
- **The wins were designed for.** `branch_machine.of` was written to have a
  dominant path, and it has one. That demonstrates the mechanism works; it is
  not evidence about how often the mechanism applies to code nobody wrote for
  it.
- **Windows power plan is Balanced, not a fixed-frequency governor**
  (`methodology.md` §3.1). The measured floor of 1.0% is under the gate anyway.
- **No `perf` cross-check.** `methodology.md` §6's Level 2 validation cannot run
  on this target (ADR-10), so the profiler's hot-path ranking has never been
  checked against an independent oracle. Level 1 hand verification in Phase 9 is
  all that stands behind it.
- **`-O1` and `-O2` are indistinguishable on five of eight programs.** Not a
  threat to the PGO numbers, but visible in §3 and worth knowing: the extra
  `-O2` passes earn their keep only on `loop_kernel`, `nbody` and `loop_sum`.

**Reproduced?** The `nested_math.of` result reproduces Phase 11's independent
measurement of the same program a day earlier — 5.5% then, 5.2% here, 4.1% in
the attribution session. The attribution session re-measured all eight programs
and agreed with this one on every sign, and on every magnitude to within 1.5
points.
